## B1 — blocking
Claim: The shell-termination rule and its conformance criterion enumerate the terminating constructs and omit `set -e`, which ends an interactive shell on the next failing command exactly as `exit` does.
Location: `skills/command-blocks.md:51-55` (the rule) and `:70-72` (criterion 6)
Evidence: **Verified by running.** `printf 'set -e\nfalse\necho STILL-ALIVE\n' | bash -i` → shell exits, rc=1, `STILL-ALIVE` never printed. Same sequence under `zsh -i` → rc=1, `STILL-ALIVE` never printed (this machine's default interactive shell is zsh). Control, the same sequence with `set -e` removed under `bash -i` → the shell survives and prints `STILL-ALIVE`. So a block opening `set -e` terminates the session on any failing command, while satisfying all six criteria as written: `:70-72` bars only "`exit`, `exec`, or `logout`, and no `|| { …; exit; }` guard," and `:51-52` names the same four. Verified by running `git grep -n "set -e" 81bd2de -- '*.md'` → no hits, so no block in the tree trips this today; the exposure is prospective.
Consequence: `set -e` is the idiomatic opening line of a careful multi-command block — an author reaching for it is trying to make the block fail fast, which is the same instinct the rule is written to serve. Adding it produces precisely the window-closing failure `ed7d904` exists to prevent, and the conformance list passes it on the way. The prose rule at `:51` states the principle correctly ("A block pasted into an interactive shell must not terminate it") and would catch it; criterion 6 is what a reviewer actually runs down, and it would not. The document therefore encodes the right rule in the place that is read and the wrong rule in the place that is checked.
Fix: State criterion 6 by effect and name the constructs as instances, on the pattern `:39-42` already uses for the copy-control rule: no construct that can terminate the shell it is pasted into — `exit`, `exec`, `logout`, `|| { …; exit; }`, and `set -e` named as known instances, with adopting projects directed to add their own. Amend `:51-55` to match. If the enumeration is kept deliberately, say so and say why, because a reader cannot currently tell whether `set -e`'s absence is a decision or an oversight.
Related: `reviews/directive-dispatch-cycle-1.md` B2 — the same enumeration, restated in a second document.

## B2 — blocking
Claim: One body rule has no corresponding conformance criterion, so a block that violates it satisfies conformance as the document defines it.
Location: `skills/command-blocks.md:27-30` (the rule) against `:57-72` (Conformance criteria)
Evidence: Verified by reading at the pinned SHA, mapping each body rule to a criterion. Verbatim / no manual step inside the fence (`:15-20`) → criterion 2. Evidence capture (`:21-25`) → criterion 4. **Name remotes explicitly; do not rely on the `origin` alias (`:27-30`) → no criterion.** Copyable in the delivery surface (`:32-42`) → criterion 5. One block per turn (`:44-49`) → no criterion, defensibly so: that rule constrains a turn rather than a block, and the criteria are per-block. Must not terminate the shell (`:51-55`) → criterion 6. Criterion 1 ("Every command is valid and non-harmful") corresponds to no body rule. The section opens "Every command block satisfies all six" (`:59`), presenting the list as the conformance definition rather than as a subset.
Consequence: `git fetch origin && git rebase origin/main` satisfies all six criteria while violating a stated rule. That is not a hypothetical class: the rule's own justification is that this failure is invisible — `origin`'s protocol "is environment state, and when the environment cannot authenticate it, the failure surfaces as a downstream symptom — missing work, empty results — rather than as an auth error" (`:28-30`). The one rule whose violations do not announce themselves is the one the checklist omits, so it is the rule most dependent on a checklist and the one least served by it. The gap is live in the tree today: `skills/directive-dispatch.md:152` emits a dispatch line reading "sync, then read and execute …" with no remote named anywhere in the Track B sequence.
Fix: Add a criterion — every remote is named explicitly; no reliance on the `origin` alias — or state plainly that the six are a subset and name which body rules they do not cover, so a reviewer knows the list is not the whole check. The first is cheaper and matches how the copy-control rule was handled when it was added (`OPEN-ITEMS.md:944-946`: "Also added as a fifth conformance criterion").

## N1 — non-blocking
Claim: "Evidence" is the load-bearing word in criterion 4 and is nowhere defined; the tree's own command blocks read both ways under it.
Location: `skills/command-blocks.md:21-25` and criterion 4 at `:68`
Evidence: Verified by reading `git show 81bd2de:skills/directive-dispatch.md:132-147`. The Track B pre-flight block is `ls ~/Downloads/<stem>*` with no capture, and the surrounding prose makes its output the decision input: "The pre-flight surfaces what is there; Dave judges" (`:125-126`), "The listing is for Dave's eye; he judges what belongs" (`:146-147`). Under criterion 4 ("Any command producing evidence captures its output to a named path") that block is either non-conformant or its listing is not evidence — and `:24-25` says "If the output is not worth capturing, it was not evidence," which makes the second reading assert that the input to a go/no-go judgment is not evidence.
Consequence: An author following `skills/directive-dispatch.md`'s documented Track B sequence emits a block that a reviewer applying criterion 4 must reject, and neither document says which is right. The rule's teeth depend entirely on a word whose scope the reader has to guess, so in practice criterion 4 will be applied inconsistently — which is worse than a narrower rule applied uniformly, because the inconsistency is invisible until two people disagree about a specific block.
Fix: Scope the term in `:21-25` — for instance, output that will be cited later or that leaves the session, as against output consumed in the moment by the person running the block — and say which side the pre-flight listing falls on. If the pre-flight is meant to be exempt, `skills/directive-dispatch.md` should say so where the block is defined.
