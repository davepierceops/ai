## B1 — blocking
Claim: Rule 3's prohibition on abbreviated pointer SHAs contradicts `policies/document-metadata-policy.md`, which is `agreed`, and the tooling shipped to enforce that policy.
Location: `policies/remote-write-verification-policy.md:53-54` (Rule 3, final sentence)
Evidence: **Verified by running.** The rule reads: "State SHAs read from git. Never abbreviate a SHA that will be used as a pointer, and never invent one." Against it: `git show 81bd2de:policies/document-metadata-policy.md` (frontmatter `status: agreed`), "The record": "an abbreviated pointer against a full-length entry is the same SHA and a different string, so a checker either requires both to match character-for-character or normalizes through `git rev-parse` first" — the policy contemplates an abbreviated pointer as valid and specifies how a checker must handle it. `bin/aimeta/expedited.py` implements the second option: its module docstring states the rule "needs git to resolve an abbreviation," `resolve()` runs `git rev-parse --verify --quiet <sha>^{commit}`, and `names_sha()` compares *resolved* SHAs on both sides with the comment "either side may be the abbreviated one." `git show 81bd2de:skills/spec-review-cycle.md:184` specifies the review-artifact header as `Reviewed: <path> @ <sha, short or full>`. `bin/check-frontmatter --all` exits 0 over 47 in-scope files, so the tree as it stands satisfies the agreed policy and the tooling — not this rule. Live instances: `policies/document-metadata-policy.md`'s own frontmatter carries `last-reviewed: reviews/expedited-log.md @ 1f5b7153dc3140f500ceb5575f459f1098b23de0` (full), while the directive under execution pins `origin/main @ 81bd2de` (abbreviated), and `reviews/document-metadata-policy-cycle-12.md`'s header cites `67b586a`, `b3c4c72`, and `321ff5a` — all abbreviated pointers this rule forbids.
Consequence: `last-reviewed:` is the repository's most load-bearing pointer, and it is governed by an `agreed` policy that permits abbreviation and by a checker built to normalize it. This draft policy forbids it outright and scopes itself to "any tool-mediated remote mutation," so nothing in its text tells a reader that `last-reviewed` is out of its reach. An agent holding both will either rewrite conformant frontmatter to satisfy this rule or violate this rule to satisfy the agreed one, and cannot tell which is intended. A draft policy that contradicts an agreed policy is the more serious direction of the two: agreeing it would put the repository in the state `policies/document-metadata-policy.md`'s supersession clause exists to prevent — two canonical conventions live at once, with no supersession record saying which won.
Fix: Scope the sentence to where it earns its keep. The two sentences around it are about provenance — SHAs quoted from a write call's return, restated from memory, or invented — and that is the real rule: never state a SHA you did not read from git, and never abbreviate one in a context where the reader cannot resolve it (a dispatch block pasted before the clone exists, a report leaving the session). Say that, and defer to `policies/document-metadata-policy.md` for `last-reviewed`. If a blanket prohibition is genuinely intended, it is an edit to an agreed policy and to `bin/aimeta/expedited.py`, and belongs in a cycle over those.

## N1 — non-blocking

Location: `policies/remote-write-verification-policy.md:56-65` and `:67-78`
Evidence: Verified by reading `git show 81bd2de:skills/directive-dispatch.md:114-220`. Track B writes through a local clone (`mv`, `git add`, `git commit`) rather than a mediated transport, and carries its own verification rule at `:191-192`: "**Verification moves to Dave.** The agent must not report a Track B write as verified — only what Dave reported," plus "**Commit, not push**" at `:185-186`. The citation is one-way: `skills/directive-dispatch.md` cites this policy twice (`:72`, `:93`); this policy's "Relationship to existing rules" cites only `skills/spec-review-cycle.md`. Confirmed by running `git show 81bd2de:decisions/log.md`: `DEC-000080` audited this policy and the small-writes rule together on 2026-08-07 and retained both, describing this one as "transport-general evidence discipline" — an audit that reached the document without adding the Track B case to it.
Consequence: An agent loading this policy as its write-verification discipline gets three rules that all assume a remote it can read back from, and none that say what to do when it cannot. Track B is exactly that case, and it is the path Dave invokes when the transport is degraded — i.e. the situation this policy was written for. The operative rule is discoverable only from a skill an agent may not have loaded, so the policy is silent precisely where the failure mode it names is most likely.
Fix: Add a clause to Scope naming the case where the agent cannot verify — verification is the operator's, and the agent reports only what the operator reported — and cite `skills/directive-dispatch.md` in "Relationship to existing rules" alongside `skills/spec-review-cycle.md`. The rule already exists and is well stated; this is about putting a pointer to it in the document that owns the topic.
