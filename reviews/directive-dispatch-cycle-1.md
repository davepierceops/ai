## B1 — blocking
Claim: The document requires a sync step on every dispatch and constructs it as a command block, and its own Track B sequence has neither — the substitute is a proposal the tree records as unanalysed.
Location: `skills/directive-dispatch.md:104-106` against `:114-220`, `:152`, `:187-188`, and `:291-293`
Evidence: Verified by running (`git show 81bd2de:skills/directive-dispatch.md`, `git show 81bd2de:OPEN-ITEMS.md`). `:104-106`: "**State the sync step every time**, even when the clone should be current: a stale clone reporting missing work is evidence about the clone, not the repo. Construct it per `skills/command-blocks.md`." The Track A dispatch template at `:96-100` opens with `<sync block>` accordingly. Track B emits two command blocks — the pre-flight `ls` (`:138`) and relocate/commit/echo (`:156-165`) — and no sync block; the status line records it as intended: "Track B mechanics rewritten 2026-08-07 (… standalone sync block dropped)" (`:291-293`). What remains is the word "sync" inside `echo "sync, then read and execute <dest-path> @ $(git rev-parse HEAD)"` (`:152`), and `:187-188` requires that line be "one line, no markdown, no backticks" — plain prose, not a constructed block, carrying no remote. `OPEN-ITEMS.md:901-916` proposes exactly that phrasing under "Sync as a skill rather than a step inside every directive," records it as sourced from Dave and "Parked mid-session, not developed," and closes: "Not analysed. Interacts with the dispatch block's two-step form and with what 'self-contained' means for a directive."
Consequence: A Track B dispatch hands the executor the bare word "sync" and no mechanics. `skills/command-blocks.md:27-30` forbids relying on the `origin` alias because that failure "surfaces as a downstream symptom — missing work, empty results — rather than as an auth error," and a one-word instruction cannot name a remote, so the Track B path defeats that rule by construction. The failure mode is the exact one `:104-106` names: an executor syncs from whatever `origin` resolves to, or does not sync, reads a stale clone, and reports missing work as a fact about the repo. Beyond the mechanics, the document has adopted the resolution of an open design question while that question is recorded as unanalysed, so a reader cannot tell whether the standalone sync block was dropped by decision or by editing pressure during a same-day rewrite.
Fix: Pick one and make the document say it. Either restore a sync command block to the Track B sequence (and reconcile with `:187-188`'s plain-line constraint), or state at `:104-106` that Track B satisfies the requirement through the echoed instruction, say what the executor is to run and against which remote, and record why the two tracks differ. Either way, close or explicitly defer `OPEN-ITEMS.md:901`, and reconcile with `LEXICON.md:105-106`, which asserts a sync block precedes *every* execution block.

## N2 — non-blocking
Claim: The Track B relocate and append blocks assume the pasting shell's working directory is the clone root, and neither state it nor check it.
Location: `skills/directive-dispatch.md:156-165` and `:208-219`
Evidence: **Inferred by reading** at the pinned SHA (a controlled wrong-cwd reproduction was attempted and not permitted in this session). Both blocks mix anchors: the source is `~`-anchored (`~/Downloads/<canonical-name>`) and the destination is repo-relative, since `git add -- <dest-path>` and `git commit -q … -- <dest-path>` are pathspecs against a repository. Neither block contains a `cd`, and the only guard tests the source file's existence (`:173-175`: "The source-existence check is the only guard"). The surrounding prose states "Same-machine only" (`:189-190`) and "The relocate block never inspects the destination" (`:172`) — the second as a deliberate property — but nowhere states the assumed cwd. The re-run reasoning at `:182-184` considers the source's absence and the staged-diff no-op, and not the cwd.
Consequence: Pasted from a shell sitting in a different clone that has the same destination path, the block relocates and commits into the wrong repository and echoes a SHA that resolves there. For the *Dispatch* echo form (`:150-151`) that line is then pasted into an execution session, which syncs a repository not containing the directive and reports it missing — a failure that presents as a missing file rather than as a wrong-clone error, and that the "destination-blind" property is what removes the check against. `:189-190`'s "Same-machine only" establishes that unpushed commits are clone-local without drawing the conclusion that the block therefore has to establish which clone.
Fix: State the assumed working directory in the prose around the block, or add a repo-root branch to the existing `if…elif…else…fi` — e.g. an `elif` testing `git rev-parse --show-toplevel` against the expected clone path — which costs one branch and stays within `skills/command-blocks.md`'s fall-through requirement.
