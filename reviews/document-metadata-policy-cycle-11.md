## B1 — blocking
Claim: `### The record` — the recording rule the doc-only section explicitly defers to — still says an agreement appends *one* line and that the cited SHA resolves to a *single* entry. The same revision authorizes multi-document agreements, for which both statements are false.
Location: `policies/document-metadata-policy.md:232-238` and `:283-284`, against `:331-335`; `reviews/expedited-log.md:6`
Evidence: **Verified by running.** Built a two-entry log in which both entries name the same commit and called the checker: `bin/aimeta/expedited.py:entry_shas` returns that SHA twice, `names_sha(root, log, "01fb103")` returns `True`, and `check_pointer(root, review)` takes `(root, review)` only — no document path reaches the check, so nothing in the tool ties an entry to the document whose pointer cites it. Verified by reading for the text: N1's disposition generalized the paragraph's opening clause ("Each expedited **or doc-only** agreement appends one line…") and left the two singular claims that follow it untouched, while B3's disposition added the multi-document rule ninety-odd lines later at `:331-335` ("the log then takes one entry per document, each document's `last-reviewed` cites that same content SHA"). Before this revision the two could not collide: the expedited path's condition 1 (`:140-142`) admits exactly one in-scope document per commit, so one SHA meant one entry.
Consequence: A reader follows the doc-only section's own pointer — "It records like the expedited path (a line in `reviews/expedited-log.md` … — see 'The record')" — and lands on the single-document rule. On a three-document doc-only agreement, three entries carry the cited SHA and the policy tells the reader the SHA is what picks theirs; it is not, the document path is. Two concrete failures follow. A checker author implementing the stated rule as a uniqueness constraint rejects legitimate multi-document agreements. And the check that exists today accepts a pointer whenever *any* entry names the SHA — so document B's pointer is satisfied by document A's entry, which is exactly the "false claim of review" `bin/aimeta/expedited.py` was written to stop, in the one case where the SHA is deliberately shared.
Fix: Generalize the rest of the paragraph the way its first clause was generalized: one entry per document agreed in the commit, and the entry meant is the one naming both the cited SHA and the document carrying the pointer. Mirror it in the log header at `reviews/expedited-log.md:6` ("the SHA selects the entry"). Whether the checker should also match on path is a `bin/` change and belongs in an `OPEN-ITEMS.md` entry, not in this edit — but the policy should state the rule the checker would implement.

## N3 — non-blocking

Nothing breaks mechanically — the flip commit is frontmatter-only either way, per `bin/flip-agreed` — so the exposure is eligibility judgment, not a broken sequence.
Fix: One clause in the Sequence: whether the content commit may carry tracked paths outside the in-scope set, and if so that the reviewed SHA is the whole commit.
